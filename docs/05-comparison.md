# 05 · 与已有方案的对比

## 一句话区别

| 方案 | 它解决的核心问题 |
|---|---|
| MemGPT / Letta | 上下文窗口不够长 |
| Mem0 / Zep / Graphiti | 记忆怎么存、怎么检索、时间有效性 |
| LangGraph | 会话与长期存储分离 |
| SparkCore | 多渠道伴侣的记忆分层 |
| ai-continuity-framework #49 | 描述了"换渠道像换了个人"，未给机制 |
| **HCR** | **一个人出现在多个渠道时，怎么还是一个人** |

## 逐项对比

### vs MemGPT / Letta

```
MemGPT：主上下文 + 外部归档，模型自己决定读写
HCR：  屋（长期）+ 室（会话）+ 廊（交接）+ 人（自我）
```

MemGPT 是**单线程内的记忆管理**；HCR 是**多线程间的身份管理**。
两者可以叠加：把 MemGPT 当作"屋"的内部实现也可以。

### vs LangGraph 的 thread + store

```
LangGraph：thread 隔离会话，store 跨 thread 共享长期记忆
HCR：      室 = thread，屋 = store，廊 = 两者之间缺失的那层
```

这是最接近的结构。LangGraph 提供了**容器**，但没有定义
"换 thread 时该怎么交接"——这正是走廊要补的。

### vs SparkCore（五层记忆）

```
SparkCore：角色核心 / 结构化长期记忆 / 情节 / 工作记忆 / …
HCR：     屋 / 室 / 廊 / 人
```

SparkCore **按稳定性分层**（什么不容易变），
HCR **按空间分层**（在哪儿、从哪儿来）。
前者解决"记什么"，后者解决"在哪记、怎么接"。

两者不冲突——SparkCore 的五层可以整个塞进 HCR 的"屋"里。

### vs ai-continuity-framework #49

该项目把问题描述得非常准确：

> 提供情节记忆，但没有工作上下文（我们正聊到哪、共同的默契、对话的惯性）。

HCR 的观点是：**这个"工作上下文"不该塞进记忆系统，应该单独成层。**

把它做成记忆，会污染长期记忆；做成会话，会跟平台绑定。
所以它必须是第四层：走廊。

## HCR 的适用范围

**适合**

- 一个角色、多个渠道、同一批用户
- 陪伴型 / 长期关系型 agent
- 渠道之间会来回切换

**不适合**

- 一次性问答机器人（不需要交接）
- 多人共用一个 agent（需要先做用户隔离）
- 渠道间不需要连续性的场景（比如客服工单）

## 已知局限

1. **渠道延迟差异**：浏览器自动化的渠道可能慢几十秒，交接窗口内会出现顺序错乱
2. **不能替代会话合并**：极致的连续性仍需要共享会话，HCR 用交接换取安全
3. **规则维护成本**：六条走廊规则需要随场景调参
